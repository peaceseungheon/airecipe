# 0003. 상태 관리: SWR(서버 상태) + React 로컬 상태, 전역 스토어 미도입

- 상태: 채택됨
- 날짜: 2026-05-21

## 맥락

프론트는 두 종류의 상태를 다룬다: (1) 서버 상태 — 저장된 레시피 목록·즐겨찾기, 서버가 진실의 원천이며 캐싱·재검증·낙관적 업데이트가 필요. (2) 클라이언트 상태 — 생성 폼 입력, 스트리밍 진행 표시 등 화면 로컬. 이 둘을 한 도구로 묶으면 부적합하다(서버 상태를 useState로 관리하면 캐시·동기화를 직접 구현해야 함).

## 결정

1. **서버 상태**: **SWR**을 사용한다. `useRecipes`, `useSaveRecipe` 등 데이터 훅이 SWR로 캐싱·재검증·낙관적 업데이트를 처리한다.
2. **클라이언트 상태**: React `useState`/`useReducer`. 레시피 생성 폼·스트리밍 청크 누적 등.
3. **전역 스토어(Redux/Zustand) 미도입**: Sprint 1 범위에 전역 공유 클라이언트 상태가 없다.
4. 데이터 훅은 API와 **동일한 공유 타입**(`@/types`의 `RecipeListResponse` 등)을 import하고, 래핑된 응답(`.data`)을 unwrap하여 컴포넌트에 깔끔한 형태로 전달한다.

## 근거

- **SWR (경계면 안전 + UX)**: 서버 상태 캐싱·focus 재검증·낙관적 업데이트를 표준 방식으로 제공한다. 즐겨찾기 토글(PATCH, 멱등 설계)은 낙관적 업데이트와 잘 맞는다. 훅이 공유 타입을 쓰므로 임의 제네릭 캐스팅으로 인한 경계면 불일치를 방지한다(nextjs-fullstack 스킬).
- **React 로컬 상태**: 폼·스트리밍은 컴포넌트 수명과 일치하는 로컬 상태로 충분하다.
- **전역 스토어 미도입 (YAGNI)**: 공유 전역 상태 요구가 없는데 Redux를 도입하면 보일러플레이트만 늘어난다. 필요해지면 도입한다.

## 대안

- **React Query(TanStack Query)**: SWR과 유사하게 적합하나, Sprint 1 요구(단순 GET/저장/토글)엔 SWR이 더 경량. 향후 복잡한 캐시 무효화가 필요하면 재검토. 기각(현시점).
- **모든 상태를 useState로**: 서버 상태 캐싱·재검증을 수동 구현 → 버그 유발. 기각.
- **Redux 선도입**: 전역 상태 부재로 과함. YAGNI 위반. 기각.

## 결과

- 트레이드오프: SWR 의존성 추가. 그러나 데이터 페칭 표준화로 코드 일관성·UX가 개선된다.
- 스트리밍 생성은 SWR이 아니라 직접 fetch + ReadableStream 처리(SSE 소비)로 다룬다 — SWR은 요청/응답 1회 모델에 맞으므로 스트리밍엔 부적합. 생성 결과를 저장한 뒤에는 SWR 캐시(`/api/recipes`)를 무효화(mutate)한다.
