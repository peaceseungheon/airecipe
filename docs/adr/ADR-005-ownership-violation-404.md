# 0005. 소유권 위반을 403 대신 404 NOT_FOUND로 수렴

- 상태: 채택됨
- 날짜: 2026-05-21

## 맥락

초기 계약(2.5.3 / 4.3 / 5.3)은 보호된 단건 엔드포인트(GET/PATCH/DELETE `/api/recipes/[id]`)에서 "타인 소유 → 403 FORBIDDEN, 없음 → 404 NOT_FOUND"로 두 상태를 구분하려 했다.

backend가 구현 중 이것이 ADR-001의 RLS 이중 방어와 충돌함을 보고했다:
- RLS 정책(`auth.uid() = user_id`) + 애플리케이션 `user_id` 스코프 하에서, 타인 소유 행은 쿼리 결과가 **빈 행**으로 돌아온다.
- 즉 DB가 타인 행을 아예 반환하지 않으므로, 서버는 "타인 소유(존재함)"와 "아예 없음"을 **구분할 수 없다**.
- 403을 내리려면 `user_id` 필터 없이 조회해 소유자를 별도 확인해야 하는데, 이는 RLS를 우회(service role)하거나 소유자 격리를 약화시켜야 한다.

## 결정

보호된 단건 엔드포인트에서 **없음·잘못된 id·타인 소유를 모두 `404 NOT_FOUND`로 수렴**한다. `403 FORBIDDEN`은 Sprint 1에서 발생시키지 않는다.

`ApiErrorCode`의 `FORBIDDEN` 멤버는 타입에서 제거하지 않고 **예약**으로 보존한다(주석으로 미사용 명시). 향후 공유 레시피 등 명시적 권한 거부 시나리오에 대비.

## 근거

- **격리 일관성(ADR-001 준수)**: 403 구분을 강제하면 RLS 우회나 격리 약화가 필요해 ADR-001(이중 방어)과 모순된다. 404 수렴은 RLS 격리의 자연스러운 귀결이다.
- **존재 은닉(보안)**: 403은 "그 id의 레시피가 존재한다"는 정보를 비소유자에게 누출한다(IDOR 정보 누설). 404 통일은 타인에게 리소스 존재 여부 자체를 숨겨 더 안전하다.
- **단순성**: 소유자 확인을 위한 추가 조회·service role 경로가 사라져 구현·검증이 단순해진다.
- **타입 보존(경계면 안정성)**: `FORBIDDEN`을 타입에서 제거하면 향후 재도입 시 또 계약 변경이 필요하고 프론트 분기 코드를 깨뜨릴 수 있다. 예약 유지가 안전하다.

## 대안

- **service role로 소유자 확인 후 403**: RLS 우회 경로가 생겨 격리 약화 + IDOR 정보 누설. 기각.
- **`FORBIDDEN`을 타입에서 삭제**: 향후 공유 기능 도입 시 재추가 비용·프론트 호환성 리스크. 예약 보존이 우월. 기각.

## 결과

- 계약 정정: 2.5.3 / 4.3 / 5.3 에러 절, 0.2 에러 표(403 "예약"·404 "타인 소유 포함"), 0.3 인증 경계 표.
- 타입 정정: `src/types/api.ts` `ApiErrorCode`에 `FORBIDDEN` 미사용 주석.
- backend: 단건 엔드포인트 3종 모두 404 통일(이미 구현됨). docs/api/recipes.md 구현 노트와 일치.
- frontend: `/recipe/[id]` 등에서 타인/없음을 동일 "찾을 수 없음" UI로 처리(403 분기 불필요).
- QA: 검증 단언에서 "타인 소유 → 403" 기대를 "타인 소유 → 404"로 갱신.
- 관련: ADR-001(RLS 이중 방어), ADR-004(단건 조회 추가).
