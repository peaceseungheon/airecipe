# 0004. 단건 조회 엔드포인트 GET /api/recipes/[id] 추가

- 상태: 채택됨
- 날짜: 2026-05-21

## 맥락

초기 계약(Sprint 1)은 레시피 조회 수단으로 목록 `GET /api/recipes`만 두었다. 그러나 보호 페이지 `/recipe/[id]`(저장된 레시피 상세)는 다음 진입 경로를 지원해야 한다:
- 딥링크/북마크로 직접 진입
- 페이지 새로고침
- 외부에서 URL로 진입

이 경우 목록 캐시에서 `find(id)`로 해결하려 하면 깨진다:
- (a) 목록을 거치지 않고 진입하면 캐시가 비어 있다.
- (b) 페이지네이션으로 해당 id가 현재 로드된 페이지에 없을 수 있다.

frontend가 `/recipe/[id]` 구현 중 이 누락을 발견하고 단건 조회 추가를 요청했다.

## 결정

`GET /api/recipes/[id]` 엔드포인트를 추가한다.
- 인증 필요, 소유자 격리(본인 것만). 타인 소유·없음 모두 `404 NOT_FOUND`로 수렴(아래 갱신 참조).
  > **갱신(ADR-005)**: 본 ADR 작성 시 "타인 소유 → 403"으로 기재했으나, RLS 격리상 타인/없음 구분이 불가하여 ADR-005에서 모두 `404 NOT_FOUND`로 수렴하도록 정정했다. 이 항목의 권한 거부 코드는 ADR-005를 따른다.
- 응답: `GetRecipeResponse = ApiResponse<Recipe>` (`{ data: Recipe }`) — 목록의 `Recipe`와 **동일 shape** (저장된 레시피, id 포함).
- 새 도메인 타입은 도입하지 않는다 — 기존 `Recipe` 재사용.

## 근거

- **정확성**: 단건 조회는 목록 캐시 의존(페이지네이션·직접 진입에서 깨짐)을 제거하는 유일하게 견고한 방법이다.
- **타입 재사용(YAGNI 준수)**: 응답이 기존 `Recipe`와 동일하므로 새 타입 없이 `ApiResponse<Recipe>` 별칭만 추가. 경계면 단순 유지.
- **일관성**: 인증·소유자 격리·에러 코드를 기존 보호 엔드포인트(PATCH/DELETE [id])와 동일 규약으로 맞춤 — RLS + user_id 스코프 이중 방어(ADR-001).

## 대안

- **목록 캐시 find로만 처리**: (a)(b) 시나리오에서 깨짐. 기각.
- **목록 API에 단건 필터(?id=) 추가**: 목록 응답은 `{data: Recipe[], meta}` 래핑이라 단건 의미와 불일치. 별도 엔드포인트가 명확. 기각.

## 결과

- 트레이드오프: 엔드포인트 1개·route 파일 1개 추가. 미미하다.
- 영향: 계약서 2.5절, `src/types/api.ts`의 `GetRecipeResponse`, 6절 매핑표·0.3 인증 경계 표에 반영. backend는 GET [id] route 구현, frontend는 `useRecipe`를 이 엔드포인트 기준으로 구현(목록 캐시 fallback 제거 가능).
- 관련 불변식: 응답은 `Recipe`(id 포함) — `GeneratedRecipe`와 혼동 금지(불변식 #2).
