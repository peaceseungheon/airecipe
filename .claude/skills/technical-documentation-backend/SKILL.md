# 기술 문서 작성 표준 (레시피 앱)

이 프로젝트는 철저한 문서화를 핵심 요구사항으로 한다. 문서는 코드와 함께 진화해야 하며, 결정의 "왜"를 보존하는 것이 목적이다. 단, 코드가 이미 말하는 "무엇"을 중복 서술하지 않는다.

## 문서 종류와 위치

| 문서 | 위치 | 목적 | 갱신 시점 |
|------|------|------|----------|
| **ADR** | `docs/adr/NNNN-title.md` | 아키텍처/패턴 결정의 맥락·근거·대안 | 중요한 설계 결정 시 |
| **AGENTS.md** | 루트 + 주요 디렉토리 | 해당 디렉토리의 역할·규약·진입점 | 모듈 구조 변경 시 |
| **API 문서** | `docs/api/` | 엔드포인트·요청/응답 계약 | API 추가/변경 시 |
| **README** | 루트 | 셋업·실행·아키텍처 개요 | 셋업 절차 변경 시 |
| **코드 주석** | 인라인 | "왜"가 비자명할 때만 | 비자명한 결정 발생 시 |

## ADR (Architecture Decision Record)

중요한 결정마다 하나씩. 번호순으로 누적하며 과거 ADR을 삭제하지 않는다(폐기 시 "Superseded by NNNN" 표시).

```markdown
# NNNN. {결정 제목}

- 상태: 제안됨 | 채택됨 | 폐기됨(→ NNNN)
- 날짜: YYYY-MM-DD

## 맥락
{어떤 문제·제약 때문에 결정이 필요한가}

## 결정
{무엇을 선택했는가}

## 근거
{왜 이 선택인가 — 디자인 패턴 선택 시 어떤 문제를 해결하는지}

## 대안
{고려했으나 버린 선택지와 이유}

## 결과
{이 결정의 트레이드오프, 후속 영향}
```

> 디자인 패턴을 도입할 때마다 ADR을 남긴다. "왜 이 패턴인가"가 없으면 패턴은 부채가 된다(`software-design-principles` 스킬).

## AGENTS.md (디렉토리별)

각 주요 디렉토리(`src/services/`, `src/lib/ai/`, `src/app/api/` 등)에 그 디렉토리를 다루는 사람이 알아야 할 최소 정보를 둔다:
- 이 디렉토리의 책임 (한 줄)
- 핵심 규약 (예: "Route는 얇게, 로직은 Service로")
- 진입점/주요 파일
- 주의사항 (경계면 계약 등)

루트 AGENTS.md는 전체 아키텍처 개요 + 레이어 의존성 방향 + 각 하위 AGENTS.md 포인터를 담는다.

## API 문서

각 엔드포인트마다 계약을 명시한다. 이것이 백엔드/프론트의 공유 기준이며 경계면 버그를 예방한다.

```markdown
### GET /api/recipes

- 설명: 레시피 목록 조회
- 요청: query `?cuisine=&page=`
- 응답 200: `{ recipes: Recipe[], total: number }`  ← src/types/recipe.ts의 RecipeListResponse
- 에러: 400 (잘못된 쿼리), 500
```

> 응답 shape은 반드시 `src/types/`의 공유 타입을 참조 표기한다. 문서와 타입과 실제 응답 세 가지가 일치해야 한다.

## 코드 주석 정책

- 기본은 주석 없음. 잘 명명된 식별자가 "무엇"을 설명한다.
- 주석은 "왜"가 비자명할 때만 — 숨은 제약, 미묘한 불변식, 특정 버그 우회.
- 현재 작업/이슈 번호/"X를 위해 추가" 같은 휘발성 정보를 코드 주석에 넣지 않는다(PR/ADR에 둔다).
- 공개 인터페이스(Service/Provider 메서드)에는 입출력 계약을 간결한 한 줄 docstring으로.

## 문서 유지 원칙
- 문서는 코드 변경과 같은 작업 단위에서 갱신한다(코드 따로 문서 따로 금지).
- 오래되어 틀린 문서는 갱신하거나 삭제한다 — 틀린 문서는 없는 문서보다 나쁘다.
- 사용자 대상 설명서가 아니라 개발자/AI 에이전트 대상 기술 문서임을 기억한다.
