# 통합 정합성 검증 절차 (레시피 앱 QA)

개별 모듈이 각각 올바라도 연결 지점에서 계약이 어긋나는 **경계면 버그**가 런타임 에러의 주원인이다. `npm run build` 통과나 "API 존재 확인"은 이를 잡지 못한다. 핵심은 **양쪽을 동시에 읽고 교차 비교**하는 것이다.

## 왜 정적 리뷰로 못 잡나
- TypeScript 제네릭의 한계: `fetchJson<Recipe[]>()`는 런타임 응답이 `{ recipes: [...] }`여도 컴파일 통과.
- 빌드 통과 ≠ 정상 동작: 캐스팅·`any`·제네릭이 있으면 빌드는 성공해도 런타임 실패.
- 존재 검증 ≠ 연결 검증: "API가 있는가"와 "응답이 호출측 기대와 일치하는가"는 전혀 다른 검증.

## 검증 영역별 절차

### 1. API 응답 shape ↔ 프론트 훅 타입
1. 각 `src/app/api/**/route.ts`의 `NextResponse.json()`에 전달하는 객체 shape을 추출.
2. 대응 `src/hooks/use*.ts`가 사용하는 응답 타입을 확인.
3. shape과 타입이 일치하는지, 래핑(`{ recipes: [...] }`)을 훅이 unwrap하는지 비교.
4. snake_case(DB) → camelCase(API/UI) 변환이 Mapper에서 일관 적용됐는지 확인.

### 2. API 엔드포인트 ↔ 프론트 훅 1:1 매핑
1. `src/app/api/` 하위 모든 엔드포인트(메서드별) 목록 추출.
2. `src/hooks/`의 fetch 호출 URL 목록 추출.
3. 호출되지 않는 엔드포인트 식별 → 의도적(관리용)인지 누락인지 판단.

### 3. 파일 경로 ↔ 링크/라우터 경로
1. `src/app/` 하위 page.tsx에서 URL 패턴 추출 (`(group)` 제거, `[param]` 동적 세그먼트).
2. 코드 내 모든 `href=`, `router.push(`, `redirect(` 값 수집.
3. 각 링크가 실제 존재하는 page 경로와 매칭되는지 확인.

### 4. 상태 전이 ↔ 코드
1. 상태 전이 맵(정의된 허용 전이) 추출.
2. 모든 `status:` 업데이트 코드 검색.
3. 코드의 전이가 맵에 정의됐는지(무단 전이 없음), 맵의 전이가 코드에서 실행되는지(죽은 전이 없음) 양방향 확인.
4. 특히 AI 비동기 작업의 중간→최종 상태 전환(생성중→완료)이 누락되지 않았는지.

### 5. AI 응답 ↔ UI 소비 (이 앱 특유)
1. AI 어댑터(`src/lib/ai/`)의 tool input_schema / 반환 타입 확인.
2. 그 데이터를 소비하는 컴포넌트가 기대하는 필드와 비교.
3. AI 출력 스키마 → DTO → 공유 타입 → 컴포넌트 사이 필드명이 일관되는지.

### 6. 즉시 응답 ↔ 비동기 결과
- API가 `202 { jobId, status }`를 즉시 반환하는데 프론트가 최종 결과 필드(레시피 본문 등)에 바로 접근하지 않는지 확인.

## 검증 리포트 형식
`_workspace/03_qa_report.md`에 작성:

```markdown
# QA 통합 정합성 리포트 — {날짜}

## 통과
- [영역] {검증 항목}: OK

## 실패 (수정 필요)
- [경계면] {파일A}:{라인} ↔ {파일B}:{라인}
  - 문제: {불일치 설명}
  - 수정: {구체적 방법}
  - 통지 대상: {생산자 에이전트}, {소비자 에이전트}

## 미검증
- {이유와 함께 명시}
```

## 점진적 검증 원칙
전체 완성 후 1회가 아니라, **각 API/페이지 완성 직후** 해당 경계면을 즉시 검증한다. 버그 누적과 후속 모듈로의 전파를 막는다. 발견 즉시 생산자·소비자 양쪽 에이전트에게 파일:라인 + 수정 방법을 통지한다.
