# 소프트웨어 설계 원칙 적용 가이드

이 스킬은 레시피 앱 코드에 SOLID와 디자인 패턴을 **목적에 맞게** 적용하기 위한 판단 기준을 제공한다. 패턴을 위한 패턴은 부채다. 각 패턴은 해결하는 구체적 문제가 있을 때만 도입한다.

## 핵심 철학: 패턴은 문제에 대한 답이다

패턴을 먼저 정하고 코드를 끼워 맞추지 않는다. **먼저 문제(변경의 축, 중복, 결합)를 식별하고**, 그 문제를 해결하는 패턴을 선택한다. 패턴을 도입할 때는 "왜"를 ADR로 남긴다 (`technical-documentation` 스킬).

오버엔지니어링 신호 — 다음이면 패턴을 빼라:
- 구현체가 하나뿐인 인터페이스 (미래의 가상 확장을 위한 것)
- 한 번만 호출되는 팩토리
- 분기가 2개뿐인데 전략 패턴으로 추상화

## SOLID — 레시피 앱 맥락

| 원칙 | 이 프로젝트에서의 적용 |
|------|----------------------|
| **SRP** | Route Handler는 HTTP I/O만, 비즈니스 로직은 Service, 데이터 접근은 Repository. 컴포넌트는 표현 또는 데이터 중 하나만. |
| **OCP** | 새 AI 제공자(추천 알고리즘, 영양 계산기)를 추가할 때 기존 코드 수정 없이 확장. 전략/어댑터로 구현. |
| **LSP** | AI 어댑터 구현체들은 동일한 인터페이스 계약(입력/출력 타입)을 위반 없이 만족. |
| **ISP** | 거대한 "RecipeService"보다 용도별 인터페이스 (생성/검색/영양). 소비자가 안 쓰는 메서드에 의존하지 않게. |
| **DIP** | Service는 구체 Claude SDK가 아니라 `AIRecipeProvider` 추상에 의존. 테스트에서 목 주입 가능. |

## 레이어 아키텍처 (의존성 방향)

```
[UI 컴포넌트] → [훅] → (HTTP) → [Route Handler] → [Service] → [Repository] → [DB]
                                       │
                                       └→ [AI Provider 추상] ← [Claude 어댑터]
```

규칙: 의존성은 항상 안쪽(도메인)을 향한다. 도메인 로직(Service)이 프레임워크(Next.js)나 외부 SDK(Anthropic)에 직접 의존하지 않게 한다 — 어댑터로 격리한다.

## 패턴 선택 — 빠른 판단

이 프로젝트에서 자주 쓰이는 패턴과 트리거. 상세 구현 예시는 `references/patterns-catalog.md`를 Read로 로드한다.

| 패턴 | 언제 도입하는가 | 이 앱의 예시 |
|------|---------------|------------|
| **Repository** | 데이터 접근을 도메인 로직과 분리, 영속성 교체 가능성 | 레시피·사용자·식단 데이터 접근 |
| **Adapter** | 외부 SDK/API를 도메인 인터페이스로 감쌈 | Claude API를 `AIRecipeProvider`로 |
| **Strategy** | 런타임에 교체 가능한 알고리즘이 2개 이상 | 추천 방식(재료 기반/영양 기반/선호 기반) |
| **Factory** | 생성 로직이 복잡하거나 조건부 | AI 프롬프트 빌더, 영양 계산기 선택 |
| **Facade** | 복잡한 하위 시스템에 단순 진입점 | "레시피 생성" = AI 호출 + 영양 분석 + 저장 조합 |
| **DTO / Mapper** | 계층 간 데이터 형태 변환 (DB ↔ API ↔ UI) | snake_case DB row ↔ camelCase API 응답 |

> DTO/Mapper는 경계면 버그 예방에 직결된다. DB 필드명과 API 응답 필드명이 다르면 명시적 Mapper를 두고, 그 매핑을 단일 위치에 둔다.

## 적용 절차
1. 변경의 축을 식별한다 — 무엇이 자주 바뀌는가? (AI 제공자? 추천 로직? 데이터 소스?)
2. 그 축을 추상 뒤로 격리한다 — 인터페이스 + 구현체.
3. 구현체가 현재 하나뿐이면, 추상화를 보류하고 주석으로 확장 지점만 표시한다. 두 번째 구현체가 생길 때 추상화한다.
4. 패턴 도입을 ADR로 기록한다.

## 코드 리뷰 시 점검
- Route Handler에 비즈니스 로직이 새어 있지 않은가 (SRP).
- 외부 SDK가 Service/컴포넌트에 직접 노출되어 있지 않은가 (DIP).
- 계층 간 데이터 변환이 흩어져 있지 않고 Mapper에 모여 있는가.
- 구현체 하나짜리 불필요한 추상화가 없는가 (오버엔지니어링).
